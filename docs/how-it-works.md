# How it works

## Words

- **agent**: the program that uses this tool (a coding agent, a script). It asks questions and reads the answers.
- **owner**: the person who answers the questions of the agent. Only the owner's replies count.
- **inbox**: one address that this tool reads and sends from, with its own rules. Setup makes two: an answers inbox named `agent` by default (address `agent@<domain>`; `--name` picks another name), and `signup`. `create` adds more. Commands pick an inbox by its name with `--inbox <name>`.
- **mode**: what an inbox is for. `answers`: replies to questions. `codes`: verification codes and sign-in links, from any sender. `requests`: new work that the owner mails in.
- **tag**: the part after the `+` in an address (`agent+q1a2b3c4d5@…`). Each question, each sent mail and each sign-up gets its own tag, so a reply finds its question. One tag is one **thread** of mail: `log` groups by it, and `requests` calls it `thread`. Tags are lowercase.
- **allow list** (`allow`): who may write to an inbox. **send list** (`send`): who an inbox may send to.
- **full-access key** and **send key**: the two PostShiba API keys. The full-access key (PostShiba type "Full access") reads mail and makes inboxes; the send key (PostShiba type "Send only") can only send. Their env vars: `POSTSHIBA_FULL_API_KEY` and `POSTSHIBA_SEND_API_KEY`.
- **team**: the PostShiba team that owns the inboxes (`teamId`). **tenant**: an optional PostShiba tenant id that goes with each sent mail (`--tenant`); leave it out unless your PostShiba team uses tenants.
- **Worker token**: the secret that the CLI and the Cloudflare Worker share (`CLANKERINBOX_CF_TOKEN`).
- **DMARC aligned**: the mail server of the receiver checked that the From domain really sent the mail (SPF or DKIM passed for that same domain). Only such mail can be an answer.

## Rules

- **Two inboxes per machine.** The answers inbox (`agent@` unless you give another name) gets replies to questions; only allow-listed senders whose mail passes DMARC aligned count. `signup` (mode `codes`) gets sign-up mail; only a 4–8 digit code or a sign-in link ever leaves it, never a body.
- **Optional: a requests inbox** (mode `requests`, for example `do@`). The owner mails new work there. Mail that passes the same sender rules comes back from `poll` whole (text, forwarded part, attachment names) as a `request`, for the agent to act on. Each request gets a thread tag; a reply sent from that inbox with the tag has `Reply-To: do+<thread>@`, so the owner's answer to it comes back as a follow-up in the same thread. A tag this inbox never sent is a new request, not a follow-up.
- **A tag per use.** Each question goes out with `Reply-To: agent+<tag>@`, and each sign-up uses `signup+<tag>@`, so answers and codes reach the right agent.
- **Safety lives in the tool**, so every caller gets it:
  - Default deny: an empty allow list lets nobody in. From must be exactly one address, on the allow list (tags ignored), with a DMARC result `pass` and `aligned` from the provider (PostShiba's own check, or Cloudflare's `Authentication-Results` header on the Worker, which must name a `header.from` equal to the From domain). No trusted result counts as a fail. A From that can be read more than one way (unbalanced quotes or comments, a quote inside a comment, a backslash, more than 2048 characters) counts as no From.
  - Send list: `to` must be on the inbox's `send` list or be one of this machine's own inboxes.
  - An incoming Reply-To is never used, except by `send --reply` for mail of another agent (see [Two agents](two-agents.md)).
  - Nothing goes out with a line break or another control character in a header value (subject, from name, recipients, other headers): the command fails before the mail is sent. A question may have paragraphs but no other control characters; without `--subject`, only its first line becomes the subject.
  - Every send carries `Auto-Submitted: auto-generated` and `X-Loop: clankerinbox`. Skipped: bounces, auto-replies (`Auto-Submitted` other than `auto-generated`, `X-Autoreply`, `X-Autorespond`), bulk, list or junk `Precedence` (with parameters too), mailing-list mail (`List-Id`, `List-Unsubscribe`), an `X-Loop` of another tool, and mail that this machine sent itself (its Message-ID is in the log). Mail whose only marks are `Auto-Submitted: auto-generated` and `X-Loop: clankerinbox` is what another agent of this tool sends (PostShiba adds the first to all it sends): from an allowed sender with DMARC aligned, it is read like other mail (see [Two agents](two-agents.md)).
  - Hourly caps: sends per machine (`caps.sendPerHour`, default 30; it holds for parallel sends too, and the refusal says when the next send is possible), received mail per sender (`caps.receivePerSenderPerHour`, default 20). Answers to open questions have their own count, so other mail from the owner does not use it up. Mail over the cap is not marked read: the first `poll` after the hour reads it again.
  - Size limits: a subject has at most 998 characters, a text at most 1 MB (`caps.maxBodyBytes`). The command fails before the provider sees the mail.
  - Quoted text is stripped before an answer is read: attribution lines in English, German, Dutch, French, Spanish, Italian, Portuguese and the Scandinavian languages (also when wrapped over 2–3 lines), Outlook header blocks in those languages, signatures and mobile or Proton footers. A bottom-posted or inline reply gives the text between and after the quoted lines.
  - Signatures without a `-- ` line (Gmail writes none) are cut by the HTML part of the reply, when the mail has one (PostShiba and the Worker both keep it): the answer is the text before the first signature or quote that the mail app marked (Gmail `gmail_signature` and `gmail_quote`, Apple Mail `AppleMailSignature` and `blockquote type="cite"`, Outlook `Signature`, `appendonsend` and `divRplyFwdMsg`, Thunderbird, Yahoo and Proton marks). Without such marks, or with nothing before them (bottom-posted), the text part decides. In a text-only reply, a last paragraph of two or more lines is cut only when the quoted part of the same mail repeats it (the sender's signature in their earlier mail); else the text stays as it is. `option` reads the first line either way.
  - Mail text shown at a terminal (`poll`, `wait`, `code`, `log`) has terminal escape codes and other control characters removed. Attachment names never hold a path separator or a control character, in JSON too.
  - Email content never authorizes an action. Allowed mail that matches no open question comes back as `unmatched`, not as an answer, and every `poll` result carries a `note` that says so.
- **Providers only move mail.** Every rule above runs in the tool, the same for PostShiba and Cloudflare; one test suite (`test/shared-safety.test.ts`) runs each rule against both.
